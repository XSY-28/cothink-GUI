# CoThink 中的 agent-sync 接入修改计划

日期：2026-10-30。2026-10-31 状态更新：消费方已按本计划形成有边界的实现，agent-sync 内核不变；分阶段证据、候选安装及未验项见 [VALIDATION.md](../../../VALIDATION.md)。下文保留原设计检查点，不据计划文字宣称已完成普遍兼容。

> 后续实施使用 `executing-plans` 按阶段执行，先复核当前源码和既有未完成工作。本文件不是启动模型、安装插件、发布或执行 Git 操作的授权。

**目标：** 主模型、副模型及其插件子代理能够使用技能、完成工作，由 CoThink 汇总成果，通过现有 agent-sync 检查并接纳；父子身份、文件归属、取消与恢复不混乱。

**架构：** CoThink 管模型、插件生命周期和成果转换；agent-sync 管修改范围、输入版本、读依赖、私有修改与正式接纳。优先将同一父执行者的助手成果归入其既有 change，不向内核添加任务树或子代理协议。

**技术基础：** 当前固定 Pi 1.4.0 SDK、Node.js ≥22.19、现有 agent-sync 0.1.1 公共 JS 接口。正式检查继续使用现有 Docker 配置。

**上位文档：** [设计基线](../../../DESIGN_BASELINE.md)、[Pi 插件直接兼容方案](../specs/2026-10-30-pi-plugin-compatibility-design.md)。插件安装来源、加载器与通用 UI 兼容由总方案负责；本文只细化其与 agent-sync 的接入，不重复建立包管理系统。

## 1. 核心决定与完成标准

- 允许主、副模型及助手使用已安装技能，工作时通过已安装插件创建子代理；旧类别禁令不再作为阻断理由。
- 沿用基线中的 ONE 工作语义：一个 Team 负责人可使用插件助手，但不引入正式副模型或评审；用户明确禁用子代理时遵守。普通纯答仍是一／三次，工作 `maxCalls=null`，实际助手调用单独可见。
- 原工作目录、agent-sync 内部投影和正式 ref 不作为第三方自由写入目录；插件的独立工作副本是候选材料。
- 已有 requestId、旧内容哈希、输入版本、冲突与正式检查要求保持；未知结果不换 ID 重做，不自动重发模型请求。
- 原生插件代码不被描述为全面受 agent-sync 沙箱保护。副本与导入流程约束成果接纳，不证明任意宿主副作用都受控。
- 完成标准是“真实插件派生助手 → 技能实际使用 → 文件成果回收 → 父模型审阅 → 正式接纳 → 取消与恢复可核对”，不是安装成功或模块已 import。

**内核结论：当前接口足够支撑本方案，计划先不改 agent-sync。** 这是源码审查判断，真实插件集成仍未验证；遇到具体公共接口缺口才单独提出内核变更。

| [src/pi-runtime.js](../../../src/pi-runtime.js)：createRuntime、dispose | 资源与工具受限；dispose 为同步调用 | 接入插件创建/结束事件或进程句柄；异步清理完成前不得提前释放生命周期占用 |

| [src/gui-projection.js](../../../src/gui-projection.js)、[src/interactive.js](../../../src/interactive.js) | 展示正式成员与运行结果 | 在现有活动/详情中显示助手归属、状态、成果与取消缺口 |

新增一个消费方模块 `src/plugin-work.js`，仅集中助手生命周期、独立副本和成果导入；必要性是目前没有代码能把外部插件执行衔接到同一任务/change。不要把这些职责继续散入已很长的 workers.js，也不建设通用插件框架。若实施时已有同职责模块，扩展该模块，不重复新增。新增模块须加入根 package.json 的发行 files。

## 3. 两种执行路径

### 3.1 可复用受控工具的助手

插件允许注入会话工具或公开会话工厂时，CoThink 为助手传入当前任务资源、只读/写范围及受控工具。模型请求继续走既有 Pi 调用与记账路径；read/edit/exec 使用同一个 versioning 实例。

同一父 change 的多执行者共享调度队列，独立请求仍须核对读过的版本和旧内容；队列仅防止同时操作，不证明过期上下文仍然有效。只读阶段与题意冲突待解决阶段不能借子代理扩大权限。

### 3.2 使用原生文件工具或自行启动进程的助手

由 CoThink 准备独立工作副本，设置插件的工作目录、数据根、资源与可观测生命周期。需要 Git 的插件使用独立仓库副本，不共享正式 refs 或 agent-sync 元数据；插件自行 commit 不等于正式接纳。

不能只把 cwd 指向副本就宣称接入完成。必须验证插件的实际子进程/SDK 会话、目录选择、后代退出与成果位置；若插件忽略工作目录、派生进程不可跟踪或自带工作区逻辑，需要适配其公开扩展点，并报告具体缺口。不存在能在未核验情况下透明接管任意 Node 插件的通用钩子。

两条路径都把结果交回创建者，保留实际来源。插件自身模型调用没有进入 CoThink 请求记录时，保存插件提供的用量及来源，缺失记未知，不伪造请求记录或将父子汇总重复计费。

## 4. 生命周期与最小记录

复用当前任务记录，拟新增 `record.work.helpers` 数组；它仅描述实际出现的助手，不建立第二套任务数据库或正式 Team 阵容。运行中的句柄放在内存，重开所需的事实才持久化。

| 记录 | 必需内容与作用 |
| --- | --- |
| 身份 | helperId、parentActorId、可选 parentHelperId、插件来源/版本及插件自身 ID；防止不同插件的同名子任务混淆 |
| 输入 | 实际模型、原始任务与分工引用、changeId、inputVersion、分配的 scope/readScope、资源快照引用 |
| 执行 | 状态、开始/结束事实、会话或进程身份、取消请求与停止证据；PID 只作线索，不能单独作为重开后杀进程的依据 |
| 成果 | 文本/文件材料位置与摘要、父模型处理结论、导入 requestId、导入后的 privateVersion；纯文本无导入记录 |
| 用量 | 可取得的 usage/cost 与来源；未知保持 null，只有确认已停止且完整观测时才能给出完整总量 |

状态沿用 queued/running/completed/failed/cancelled/outcome_unknown 等现有词义。`completed` 仅指助手执行完成，不能等于文件已导入或正式版本已接纳；导入凭据与既有 acceptance 记录分开关联。旧任务没有 helpers 时按空列表读取，不回填不存在的历史。

启动前先保存身份和意图；保存失败不创建助手。父子 ID 由宿主确认，插件消息属于输入材料，不能凭自报“已检查/已接纳”生成内核凭据。进一步派生继承同一原任务和归属链，限制执行能力不能只靠父模型提示词。

## 5. 文件成果进入 agent-sync 的准确流程

### 5.1 取得一致的工作材料

1. 由父执行者已有 change 获得实际权限；没有写权限的任务只建立必要只读观察，不为了纯文本结果创建写 change。
2. 在所属 change 的队列内调用 `read({changeId, path, kind:'tree'})` 登记各个可见范围的读取依据，取得返回的 version；范围不是整项目时不能直接用 `path:'.'` 越界读取。
3. 逐文件通过公共 read 取得内容、mode 和 contentHash，确认所有返回 version 一致，写入独立副本与输入清单。快照生成期间暂停该 change 的受控写入；不混用多个版本，不用只读历史 version 查询替代读依赖登记。
4. 不能观测插件具体读取时，保守登记交付给它的完整范围，包括目录/无匹配搜索依据。可能增加冲突与刷新，但不能用缺失依赖换取“更少冲突”。技能资源与运行依赖属于任务资源，不能混入项目源文件差异。

### 5.2 固定成果并导入父草稿

1. 确认本次结果的写者及后代停止，或通过可验证的交接机制冻结；仍在写的目录不能直接扫描成“最终结果”。保存输出快照和摘要。
2. 与输入清单比较，包含新增、修改、删除、二进制和可执行位。重命名表达为删除+新增。普通 ignored 源文件不能自动忽略；只有宿主明确划分的辅助产物可排除，不能让插件改 .gitignore 来隐藏写入。
3. 验证路径、大小写别名、链接与文件类型，以及助手分配范围和父 change 范围；拒绝超范围和非法文件。缺陷保留整份成果，不静默截掉越界部分后报告全部成功。
4. 将待导入 diff 交回父模型，由其选择采用、反馈或保留。实际导入时重新核对 change 身份、状态、版本、取消标记与授权，不能沿用过期绑定。
5. 在同一 change 队列内生成并先持久保存 requestId、结果摘要和预期输入，再调用公共 edit。调用成功后关联返回 privateVersion，清除父执行者旧 reviewedVersion 与候选的可接纳标记。

现有公共接口的调用形状如下；这段是实施约定，不是已实现的新 API：

```js
await versioning.edit(parentChange.changeId, {
  requestId: persistedImport.requestId,
  expectedVersion: helper.inputVersion,
  edits: [
    { path: 'src/a.js', oldHash: input.contentHash,
      contentBase64: outputBytes.toString('base64'), mode: '100644' },
    // 新文件 oldHash 为 null；删除文件 contentBase64 为 null。
  ],
}, { signal: task.signal });
```

`parentChange` 是实际父 change；`helper` 和 `persistedImport` 来自上节持久记录；`input` 来自固定输入清单，`outputBytes` 来自冻结成果。调用前须完成上述验证。`STALE_PRIVATE`、`PRECONDITION`、`SCOPE` 等拒绝保持原义，不能吞掉。

### 5.3 父草稿已经改变时

禁止直接把 expectedVersion 改成当前版本继续导入。先取得助手原输入 A、助手结果 B、当前父草稿 C 及其读取依据，确定 C 相对 A 是否影响助手使用的输入。无影响时，宿主可重新验证后生成明确的 A/B/C 组合记录；有影响或无法判断时保留结果、提供具体差异，由父模型/助手重新处理，不静默原样重跑。

按新的输入依据形成新的结果版本后，才可分配新的导入 requestId；旧导入未知时必须先核对旧 ID。默认保守记录全可见范围，可能使两个修改不同文件的助手也需要重新核对，这是先保正确性的取舍，不通过取消版本检查解决。

### 5.4 审阅与正式接纳

父模型汇总不代表已经接纳。沿用 workers.js 的 prepare、review_required 和 accept_change 路径：任何导入都会使旧审阅标记失效；prepareChange 固定候选，父模型审阅实际候选，acceptChange 在最新正式版本上检查组合并条件推进唯一正式 ref。

对应父草稿有运行中、停止未知或未处理成果的助手时，禁止正式接纳。其他无关 change 的助手可以继续运行，不能不必要地全局串行。最终整条任务完成前必须处理所有后代及遗留结果；明确拒绝某份成果也要保留原因。

内核内部投影的直接外部修改仍应失败，不能修改 assertProjection 来迁就插件。子代理自己的 Git 分支、测试口述或输出 passed 均不替代上述接纳凭据。

## 6. 调度、取消与恢复

**避免父子死锁：** 助手默认向父执行者已有 change 交付，不能在父持有同范围且等待助手时为助手另开重叠 change。需要扩大范围时由父执行者协调 refreshChange；先处理运行中助手和未导入成果，不把新授权套给旧助手继续跑。嵌套助手同样归集到所属正式执行者，不在内核构造递归锁。

**取消顺序：** 先持久记录取消并阻止新派生、导入和接纳；传播 abort 到已登记 Pi 会话和插件句柄；等待后代退出或取得明确的未知/失败事实；最后完成日志收尾和资源释放。现有内核可以响应 abort 停止受控操作，外部助手副本不因内核释放范围而自动停止，须单独回收。已经正式接纳的内容保持，不把取消描述为撤销历史。

**展示语义：** 可以立即向用户回应“取消请求已收到”，但仍有后代未停止时显示“正在停止”或“停止未确认”。不因为 Promise.allSettled 返回就把每个 reject 当作停止成功。同步 dispose 不能承担未等待的异步清理；实际修改时逐个检查 CLI/GUI 关闭、reload、错误退出调用点。

**恢复规则：** 复用现有任务记录与 requestId 查询，不新增后台自动重跑服务。已导入但回执丢失时用 inspect(requestId) 核对，成功则恢复关联，不再次 edit。not_found 不足以证明未知动作没发生。子进程重开核对须结合进程启动身份/会话证据，不能只凭复用的 PID 杀进程。无法确认停止的助手保留停止缺口，旧结果不能自动进入新的授权。

**故障边界：** 先前代码会在 task.cancel 中将状态写为 cancelled 并关闭 journals；改造须保证助手收尾证据仍可保存。保留取消意图与停止事实的区别，避免为了增加一个状态把整套任务状态机重写。包占用与会话租约也不能在插件仍读取资源时无声释放。

## 7. 实施任务与检查点

## 9. 何时才重新评估内核修改

只有在真实案例证明公共 read/edit/prepareChange/acceptChange 无法表达必要成果，或确实需要嵌套范围转交、额外可信执行器时，才整理最小复现、现有接口失败点、消费者替代方案及内核修改代价，另行审查。
