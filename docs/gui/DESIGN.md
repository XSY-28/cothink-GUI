## 1. 推荐方案

首版采用本地 Web GUI：一个本地 Node 进程运行现有 CoThink 核心，浏览器展示界面。拟议启动入口为 `cothink gui`；这是设计中的命令，当前尚未实现。

界面采用“左侧导航＋中央交付＋右侧本轮协作”。宽窗口下右侧先呈现紧凑的参与者概览，讨论正文按需展开；侧栏可以收起。普通问答、项目问答和项目改代码共用聊天入口。项目关联决定能访问哪个项目；ONE／CoThink 决定模型协作方式，两者含义分开。

首版工作的完整交付是：选择项目 → 提交任务 → 查看执行状态 → 审阅实际差异和检查结果 → 打开独立成果目录或下载补丁。沿用当前内核接纳规则，不自动覆盖原目录。

成功标准是两条真实路径均可独立完成：新用户能配置模型并完成一次讨论；已有 Git 项目的用户能得到可查看、可带走的代码成果，并知道是否经过检查、是否已写回原目录。

### 2.1 CoThink 自己的界面重点

用户提出右侧 Team 人员和模型对话式 UI，作为继续探索的例子。本次建议围绕三个问题形成辨识度：**谁实际参与了这轮任务？批评提出了什么理由？主答如何回应并交付？** 这些问题均由已有任务、调用及成果记录回答。

| 方向 | 收益 | 代价与判断 |
| --- | --- | --- |
| 成果为主，协作在旁 | 最终答案／代码成果始终明确，同时能跟随批评与回应 | 推荐。右侧用同一任务记录呈现参与者和交流，不新增运行模式 |
| 讨论室为主 | 模型之间的实际交接最显眼 | 长答案和工具记录会淹没交付；采用其连续消息排版，不作为默认主屏 |
| 初稿与最终稿对照为主 | 容易观察文字或代码变化 | 文本差异不证明语义改进；代码保留已有 diff，首版不做另一套答案比较工作台 |

推荐组合是：中央保留完整交付，右侧成为“本轮协作”；模型消息按实际顺序连续排版，主答已有的评审处理说明放在评审之后。用户可以沿理由阅读全过程，也可以收起过程只看结果。

三项首版特色及必要性：

- **有明确作用的参与者列表。** 帮用户识别真实来源、当前负责者，并定位其记录。默认展开实际参与者；尚未参与的 Team 成员折叠在“完整阵容”中，不设独立人物卡墙。
- **连续的模型交流记录。** 初稿、评审、修订保持相邻，减少在标签之间切换记忆。每个真实回复对应一个消息块，不改写成虚构的短对话。
- **就近查看处理理由。** 直接展示修订原文中已有的“对评审意见的处理说明”，让用户对照评审判断采纳或拒绝是否合理。格式不明时展开完整原文，不加摘要请求或逐条意见数据库。

首版不增加成员人设、角色编辑器、群聊房间、模型私聊、共识分数、投票、采纳率或自动“问题已解决”标签。它们或改变原有调度，或要求当前记录不具备的判断。角色和头像仅帮助识别来源，不代表模型权威。

## 3. 界面布局

### 3.1 普通问答

```text
┌────────────────┬─────────────────────────────┬───────────────────────┐
│ CoThink        │ 讨论一个数学证明            │ 本轮协作 · 第 3 轮  × │
│ [+ 新对话]     ├─────────────────────────────┤ Team：数学讨论        │
│ [打开项目]     │ 用户问题                    │ A · 主答     已完成   │
│ [搜索对话]     │                             │ B · 评审     已完成   │
│                │ 最终答案                    │ [完整阵容]            │
│ 最近对话       │ Markdown、公式、代码块      ├───────────────────────┤
│ · 讨论一个证明 │                             │ 展开讨论后：          │
│ · 比较两种方案 │                             │ A · 初稿      [展开] │
│                │ [复制] [查看讨论]           │         ↓             │
│ 项目           │                             │ B · 评审              │
│ ▸ my-project   ├─────────────────────────────┤ [真实评审原文]        │
│ ▸ other-project│ 输入问题，或粘贴材料……      │         ↓             │
│                │ [CoThink] [Team] [思考]     │ A · 修订说明          │
│ [设置]         │ 纯答 3 次            [发送] │ [真实处理说明原文]    │
└────────────────┴─────────────────────────────┴───────────────────────┘
```

- 左栏建议宽约 240px，可收起；对话正文最大宽度约 720–800px，实际随可用空间收缩，长公式和代码块独立横向滚动。
- 无关联项目即可问答。空状态直接提供输入框，不要求先创建工作区、角色或流程。
- 对话标题默认从首条输入截取，可手动重命名，不为命名增加模型请求。
- 顶部保留标题与详情入口；模式、Team、思考档位只在输入框旁提供一套编辑入口。右侧显示所选任务的阵容快照，不提供另一套阵容编辑器。
- 讨论运行中展示真实阶段“主答中／评审中／修订中”和已用时间，不显示虚构完成百分比。右侧可以显示当前承担该阶段的模型，默认不自动展开中间正文；CLI 原有默认隐藏中间信息的约定不因 GUI 草案而改变。
- 点击“查看讨论”后，在同一右栏连续展示“主答初稿 → 评审原文 → 主答修订”，替换原方案的三个隔离标签。初稿可折叠，评审及已有处理说明方便相邻阅读；完整修订可展开或定位中央最终稿。宽度不足可展开阅读，退出恢复原位置。
- 每张卡片保留模型、角色、阶段和实际状态；标题下面只放原文或明确标记的原文节选。阶段是同一份任务记录中的调用，不能把初稿与修订包装成两个新 Agent，也不能把一个长回复拆成多轮虚构插话。
- 普通问答只调用第一位副模型评审；其他 Team 成员收在完整阵容中并标明“本轮未参与”。首轮尚未提交时可显示当前配置；提交后展示冻结阵容，已配置但尚未请求的角色标“尚未调用”。ONE 纯答只显示主模型参与，不保留空的评审对话；ONE 工作仍可显示实际插件助手及其独立身份／用量，不创建正式 Team 副模型。
- 输入框 Team 表示下一条配置，右侧“第 N 轮／本轮协作”表示所选任务历史。点击旧答案的“查看讨论”才显式切到该轮快照，不用当前配置重写旧作者，也不随页面滚动悄悄换任务。
- 评审收到初稿，主答收到评审，但评审没有再次收到最终修订。界面不显示“评审确认最终稿”“全员同意”或“共识已达成”。主答的“已采纳”是其处理说明，不等于程序已验证观点正确；重要分歧仍在最终答案正文。
- 点击参与者定位或筛选其已有记录，不另开模型私聊；只有两名参与者时省略复杂筛选控件。首版不支持指定某个成员继续说话，后续用户消息仍进入统一主答路径。
- ONE 和 CoThink 可在同一聊天内切换；运行中变更只影响下一条，界面明确标注。Team 在任务进行时锁定，沿用当前行为。

### 3.2 项目任务与代码成果

```text
┌─────────────────┬───────────────────────────┬─────────────────────────┐
│ CoThink         │ 修复导入时的边界错误      │ [协作] [变更] [检查]  × │
│ [+ 新对话]      │ my-project · 查看起点     ├─────────────────────────┤
│ [打开项目]      ├───────────────────────────┤ 本次交付：起点 → 最终版 │
│                 │ 用户任务                  │ 修改  src/parser.js     │
│ 最近对话        │                           │ 新增  test/parser.test… │
│ · 讨论一个证明  │ 正在执行 · 已调用 8 次    │                         │
│                 │ [查看执行详情]    [停止]  │ 选中文件的行内差异      │
│ ▾ my-project    │                           │ - 删除内容              │
│   修复导入错误 ●│ 完成后：                  │ + 新增内容              │
│   调整错误提示  │ 结果说明与未解决问题      │                         │
│ ▸ other-project │ [查看成果] [下载补丁]     │ 检查：通过／未配置／失败│
│                 │ [打开成果目录]            │                         │
│                 ├───────────────────────────┤ 成果已保存至独立目录    │
│                 │ 输入下一条……              │ 尚未写回原项目          │
│ [设置]          │ [CoThink] [Team] [思考]   │                         │
└─────────────────┴───────────────────────────┴─────────────────────────┘
```

这是结构草图，不是已经完成的视觉稿；文件名、调用次数和检查状态都是说明布局的示例。

- 项目会话保留同一聊天入口，模型按现有规则选择回答或执行工作。不再增加另一套“开发模式”算法。
- 工作进行时，主区保留紧凑状态和停止按钮；右侧协作页先显示实际主模型与成员，任务、反馈和工具记录按需展开。变更与检查复用同一右栏切换，不再增加一个独立 Team 列。
- **变更**：先列本次改变的文件，再显示所选文件的行内 diff。首版不做可编辑代码区、完整 IDE 或左右双份编辑器。
- **协作**：按已有来源展示委派、成员回复与具体反馈；工具活动折叠在“执行记录”中。没有记录证明内容交接时，只显示并列活动，不画成成员都看到了彼此消息的共享群聊。名称用“执行记录”，避免让用户误以为这是可输入任意宿主命令的终端。
- 成员完成与主模型收到结果分别依据实际记录，不能把完成自动说成已阅读。并行活动按真实时间展示而不虚构轮流发言；调用改派后的历史作者取当次请求，不取成员最新模型名。
- **检查**：列真实检查命令、结果、对应版本与日志。“未配置检查”不能显示为“测试通过”。
- 接纳仍由现有领导模型与 agent-sync 完成。用户的“查看变更”不新增一道人工接纳协议，界面不提供能跳过内核检查的“接受”按钮。
- 三种事实分开展示：私有草稿、已接纳到 CoThink 项目版本、已生成本次最终成果。任意一种都不自动等于已修改用户原分支。
- 取消或失败可能已经留下已接纳的部分成果；保留其版本、检查和差异，同时显示“任务未完整完成”。停止不承诺撤销已接纳修改。
- 首版提供下载完整补丁和打开独立成果目录；原项目合并、提交、推送继续由用户在现有 Git 工具中明确执行。

### 3.3 收缩与视觉方向

- 宽窗口默认显示约 220–260px 的紧凑协作概览，正文保持主要阅读空间；讨论或差异展开后右栏约 380–520px。优先给中央正文保留至少约 520px，空间不足先收起左栏，再将右栏改为覆盖式面板。紧凑窗口默认收起协作概览，用“查看讨论／查看协作”打开；用户手动收起后不因模型发言自动弹回。查看较宽差异可把详情扩展为主要阅读区，收起后回到原滚动位置。
- 以 1280×800、1024×768、800×600 三种视口作为首版检查点；输入区、活跃任务返回入口和停止按钮始终可达。覆盖式面板用 Esc 关闭并把焦点还给触发按钮，关闭面板不取消任务。手机仅保证基本可读，首版不承诺完整移动开发体验。
- 倾向低饱和灰底、清晰细分隔线、一个克制的强调色；浅色与深色使用同一套布局。避免为每个模型设置大色块或头像阵列。
- 正文约 16px、行高约 1.7，中文优先使用本机可读字体；代码使用本机等宽字体。字体与应用资源不依赖运行时外部 CDN。
- 动效仅用于展开、状态切换和焦点反馈。错误和状态同时有文字，不能只靠红绿颜色辨认。
- Enter 发送，Shift+Enter 换行；中文输入法组词时 Enter 不发送。浏览历史时不强拉到最底部。

## 4. 第一版功能范围

| 功能 | 首版交付边界 | 用户需要它的原因 |
| --- | --- | --- |
| 首次设置 | 复用现有凭据；API Key 与自定义服务商表单；建立具名 Team | 新用户能独立完成第一次请求 |
| OAuth | 复用已有 Pi 登录；首版尚未覆盖的授权流程明确引导现有 CLI | 不另造服务商认证系统，也不假称所有登录流程已有 GUI |
| 持续聊天 | 新建、恢复、标题搜索、手动命名、草稿和复制 | 解决日常阅读和继续使用 |
| 模型协作 | ONE／CoThink、Team 选择与基础管理、实际支持的思考档位 | 使用已经实现的核心差异 |
| 讨论详情 | 本轮参与者；连续排列的初稿、评审和修订；已有处理说明与阶段状态 | 用户能跟随批评和回应，检查讨论是否有实际价值 |
| 项目入口 | 最近项目与路径输入；显示明确目录、Git 起点和未提交状态 | 让执行范围和起点可见 |
| 项目执行 | 现有 start_work、领导与成员工作、等待、取消、检查、接纳 | 首版确实能完成项目改代码 |
| 工作详情 | 实际成员与有来源的交流；折叠执行记录、任务相关差异、检查结果 | 用户能判断谁做了什么、产物及其验证依据 |
| 成果交付 | 固定版本 diff、含二进制的完整补丁下载、打开成果目录 | 代码能被审阅和带走 |
| 执行环境 | 展示并编辑现有全局 Docker／镜像／检查配置，标明后续任务生效，保留已有验证规则 | 配置缺失时可在 GUI 内定位并处理 |
| 运行状态 | 已发调用数、阶段、停止、失败／部分／未知状态、已知用量 | 长任务可控，失败也能回看 |

Markdown 导出和设置页中的完整更新记录属于可顺延项：接入简单时带上，不作为两条核心路径的发布门槛。现有按版本一次的启动更新提示规则仍需保持，不能因暂缓完整记录面板而悄悄删除；布局图中的导出按钮相应可延后。

首版输入以文本、多行粘贴及项目文件路径为主。项目文件由现有工作工具读取；不新建文件索引。PDF/OCR、图片问答、资料库、任意附件解析放到后续，避免扩大本轮模型输入与存储合同。

技能继续按现有配置加载，详情展示已预载项；GUI 首版不做包市场或 JS 插件加载器。会话分支树、自动归档、跨设备同步、后台任务队列、自由终端、一键覆盖原目录与 Git 推送也不进入首版。

首个版本采用一个 GUI 宿主同时执行一条用户任务；任务内部的成员并行沿用现有核心。运行中可只读查看其他历史，但不切换正在运行的 runtime，也不自动排队提交。后续消息保留为草稿。浏览其他页面时常驻紧凑状态“正在执行：任务标题 · 返回任务 · 停止”；历史页标明只读并停用发送，避免停止入口随导航消失。

## 5. 必须设计清楚的使用过程

### 5.1 首次启动

先读取已有 CoThink 配置和历史。已有配置直接进入；未配置时填写服务商和 Key、选择主副模型、命名 Team。保存设置不调用生成模型，不自动发送试题。模型目录请求或 OAuth 操作按实际行为说明。

浏览器只把用户本次输入的凭据提交给本机宿主；宿主使用现有 Pi 认证保存方法。历史凭据不回传页面、不存 localStorage、不随聊天导出。受限 OAuth 的 CLI 引导与普通 API Key 的 GUI 路径分别标明。

### 5.2 打开项目

本地 Web 不能把浏览器“上传文件夹”冒充可直接读写的宿主仓库。首版默认提出启动目录供用户确认，也可从历史项目选择或输入绝对路径；没有明确选择前，GUI 进程 cwd 不构成项目授权。

选择后先只读核对有效 Git HEAD、当前工作目录变化和已有 agent-sync 项目状态。显示实际起点：已有项目沿用正式版本；新项目按现有初始化规则。若原目录有未提交修改，明确说明这些内容不会自动进入工作起点，也不会被自动覆盖，不代用户 stash、commit 或迁移。

继续修改时，输入框上方显示“基于 CoThink 当前成果 · 原项目未写回”，可展开实际版本。如果其他任务已推进正式版本，显示更新后的起点，不能永远称为“上次成果”；执行最终以现有内核实际授予的版本为准。

旧项目需要迁移时，界面显示原因及现有显式迁移入口，首版不自动接管。关联目录跟随会话保存；已产生内容的会话不静默更换项目，换目录新建会话。

Shell 和非空正式检查沿用固定 Docker 环境；缺配置、镜像或依赖时显示具体缺口。设置页复用现有 work 配置字段，明确标注“共享全局设置，对后续任务生效”，不误称为每项目独立配置。项目提交前展示实际解析的检查命令；未显式配置时沿用现有 package.json test 推导。不能把“环境可连接”说成“项目检查已通过”，也不回退到宿主 Shell。

### 5.3 提交、运行与返回

提交时冻结模式、Team、参数和已绑定项目。项目会话提交前显示“纯答 1／3 次；进入工作后调用次数不设上限”；执行后显示实际调用数和可用停止按钮。输出额度、未知费用仍依当前政策展示。

普通未关联项目的聊天由宿主限制为问答；使用明确的中性 cwd，并关闭项目上下文文件的自动加载，避免启动目录的 AGENTS 等材料意外进入上下文。用户显式配置的全局技能仍按既有政策提供。绑定项目后，模型可在首次主请求选择 start_work。此限制需要实际工具权限与提示同时一致，不能只隐藏按钮。这是拟议的新 GUI 会话边界；旧 CLI 会话的既有行为保留，CLI 恢复这种新会话时也必须通过共享会话控制识别明确的“未关联项目”状态。

首版先实现可靠的阶段与工作活动更新、阶段结束后完整正文。若增加逐字显示，流中的修订稿明确为“生成中”，完成后才投影为最终稿；不以流式展示作为首版必须另建一套协议的理由。

### 5.4 刷新、断线与取消

浏览器刷新或关闭不会把已发任务重新发送。Node 宿主仍运行时可重新连接查看同一任务；宿主退出或崩溃后只恢复已保存事实，不自动恢复生成。界面分别显示“连接中断”和“请求结果未知”。

发送按钮防连击之外，宿主还需识别同一次提交。建议将 submissionId 关联存入现有任务记录，在首次模型请求前落盘；确认响应丢失时只查询原提交，不换 ID 自动再发。它只解决 UI 重连和双击的重复消耗，不新增任务队列或重试系统。

停止调用现有整任务取消，等待实际停止结果；已保存文本、执行日志和部分成果继续可查。退出宿主时提示活跃任务并走已有取消路径，不能以关掉网页冒充任务已停止。

## 6. 技术方案比较

| 方案 | 复用方式 | 新增维护负担 | 判断 |
| --- | --- | --- | --- |
| 本地 Web＋Node | 浏览器 UI 经本机 HTTP 调用现有 Node 核心 | 一个轻量本机接口、静态资源打包；项目路径与系统打开动作由宿主适配 | **推荐首版**，可沿用当前 npm 分发和 Node 环境 |
| Electron 桌面 | 同一 Web UI，Node 宿主放桌面进程侧 | 桌面打包、签名、更新、窗口生命周期与多平台验收 | 若首版必须双击安装、原生目录选择，可改选；主流程设计不变 |
| Tauri＋Node sidecar | 系统 WebView 显示 UI，另打包 Node 核心进程 | Rust／WebView／Node sidecar 的生命周期和跨平台打包 | 当前复用 Node 核心时层次更多，暂不优先 |

Electron 的主进程运行在 Node 环境；Tauri 官方提供 Node sidecar 指引。以上维护成本判断是针对本项目的推断，没有做安装体积或性能实测。未来打包桌面端时只选择一个首要交付形态，不承诺同时长期维护三套宿主。

推荐实现选择：React 负责页面状态，Vite 仅用于构建前端；发布包中的 Node 宿主直接提供本地静态资源。无需 SSR、云服务器、账号体系或新数据库。普通命令使用 HTTP，请求状态使用 SSE 单向推送；重新连接仅恢复观察，不重复模型请求。

所有 UI 资源随包交付；模型连接仍沿用用户已有服务商和网络条件，不因 GUI 变成本地离线模型。

### 必须做的少量调整

1. **提取共享会话控制。** 模式保存、Team 切换、恢复、写锁与提交冻结目前在 `interactive.js` 的闭包中。将这些非 UI 行为提取为一个小模块，由 CLI 与 GUI 共用；终端组件留在原文件。没有这一提取，两个界面容易出现不同的恢复和保存规则。
2. **增加本地 GUI 宿主和浏览器界面。** 宿主持有 runtime、会话写锁和活跃任务；前端只负责展示及用户操作。没有宿主，浏览器不能安全复用 Node、Pi 和本地项目工具。前端目录、本地宿主、共享会话模块是预计主要新增边界，不先建设通用插件或 RPC 框架。
3. **补状态快照通知。** 当前 onProgress 覆盖部分阶段、工具开始和内核活动，成员与工具结束未全部向外推送。复用现有保存点发轻量快照通知，由宿主节流推送；不另建事件数据库。原事件 type=git 对外投影为“工作活动”，不能把所有动作都叫 Git 操作。
4. **固定工作起点和终点。** 现有 work.version 会随接纳更新。新增 work.startVersion，记录进入工作时的正式版本；完成任务的总 diff、补丁和成果目录绑定 startVersion → 已保存的 work.version，不使用查询时的当前项目 tip。失败或响应丢失时只从本任务接纳 requestId 的回执恢复 acceptedVersion；无法确认就提示缺口。旧任务起点只能从可信获权记录恢复，不能猜当前 HEAD。若期间存在其他客户端接纳，该版本区间可能包含并发成果，界面注明“交付版本差异”，每位执行者的贡献另看 change 记录，不能把全部差异冒称本任务独有贡献。
5. **补一次提交的确认关联。** 复用 task 记录保存 submissionId，返回已有 taskId；GUI 不通过再次生成探测上次是否成功。需要同会话串行校验和持久记录，不能只靠浏览器按钮禁用。
6. **区分实时状态与离线记录。** `readTask()` 会把历史 running 投影为 outcome_unknown。活跃任务应从宿主持有的 task 读取；宿主不存在时才采用恢复语义，避免刷新页面就把正在执行的任务误标未知。

新增 startVersion 和 submissionId 各自解决“本次交付从哪版比较”和“确认丢失时避免重复发送”，放入既有记录即可。项目列表从主会话 cwd 和已有工作记录聚合；未绑定项目的 GUI 聊天需要明确保存关联为空，不能从进程 cwd 推断。旧会话沿用原 cwd 解释，进入项目工作前显示并确认关联。

GUI 使用与 CLI 相同的 `COTHINK_HOME`。同一会话的跨入口写锁继续有效；被另一入口占用时可只读查看，不能强抢锁。不要误用归档时代的 storage 会话模型替代当前 Pi SessionManager。

### 协作 UI 只投影现有记录

Team 面板使用 task.team 的历史快照；是否实际参与取 stages／requests／members，不能只从配置推测。卡片身份使用 taskId、stageId、callId 或既有 toolCallId，而非只按模型名去重；身份展示区分逻辑角色与请求记录中的实际模型。当前配置不支持同一模型同时占主答和评审席位，GUI 不借呈现调整扩大这项规则。

问答交流可直接由 draft／review／revision 的请求原文、来源和 finalCallId 投影。修订材料已经记录评审 author、text、callId，参见 `src/context.js:41`、`:54`；处理说明约定见 `prompts/revision.md`。没有逐条批评与回应的结构化对应关系，首版不自动推断意见状态、争议数量或采纳率。

工作交流不能只靠 members 当前快照重建：feedback 可改派模型，members.feedback 只有字符串，delegate／feedback／collect 也未统一落入 task.tools。精确交接应只读关联已有领导 request 的 toolCall、Pi session 的 toolResult 和对应 memberId，再读取实际成员回复；依据见 `src/workers.js:611`、`:663`、`:718`、`:793`、`:1046` 及 `src/presentation.js:146`。这是一段只读展示转换，不新增 Agent 身份表、聊天消息表、讨论房间或模型摘要请求。

缺少关联记录时显示“已保存的委派／成员结果／反馈”，保留原文和来源，不假称准确的传递时刻或已被主答读取。旧任务没有 Team 快照时显示“当时未记录 Team”；身份未知则标“来源未记录”；回复部分完成或结果未知时保留对应状态。无法识别修订说明标题时完整展示原文。

### 本地接口边界

接口围绕少量用户操作：列出／新建／打开主会话、读取／保存模型和 Team、关联项目、提交／查询／取消任务、读取讨论、读取固定版本差异和分页日志、导出补丁、打开可信成果目录。

宿主只监听 loopback，验证 Host／Origin，并用本次启动凭据保护读写接口。页面收到的是为 UI 挑选且脱敏的数据，不是整份 auth 或原始模型请求；模型输出按不可信 Markdown 渲染，不执行 HTML、脚本或自动加载远程资源。打开成果目录只接受已记录成果路径，使用受控系统打开动作，不开放任意宿主命令接口。

这些是本机 Web 接口必须保留的边界，不扩展成云端用户权限系统。

## 8. 实施顺序与验收标准

本节是已获开工授权的实施顺序与验收依据。

1. **先完成共享会话提取与只读 GUI。** 现有 CLI 行为不变；GUI 能列历史、正确投影最终稿、查看讨论与已保存成果。此时零生成即可核对数据复用。
2. **接通连续问答和配置。** 覆盖首次配置、ONE／CoThink、Team、参数冻结、取消、保存失败、重复发送和页面重连。
3. **接通项目工作与成果。** 覆盖项目起点、执行环境、真实委派状态、工具日志、固定版本差异、检查结果、补丁和成果目录。
4. **按实际入口验收并交付。** 本地 fixture 验证与真实模型内容验收分别记录；最后做 macOS 和 Windows 浏览器的中文输入、复制、长文、公式和窄窗口检查。桌面安装包验收属于选择桌面交付后的另一项工作。

| 场景 | 可检查的通过标准 |
| --- | --- |
| 首次使用 | API Key 路径能从空配置进入首次问答；纯设置无生成调用；已有历史可在凭据缺失时只读查看 |
| 一／三次问答 | GUI 和 CLI 同一配置下仍为 ONE 一次、讨论三次；主屏最终稿与详情保存原文一致 |
| 协作呈现 | 三次真实调用对应三个有来源的消息块；未参与成员不显示为已调用；历史阵容不受当前设置影响；不生成评审确认或虚构共识 |
| 工作交流 | 委派、回复、反馈的作者及交接与已有请求／工具结果对应；改派不重写历史作者；缺记录时明确退化为活动记录 |
| 连续会话 | CLI → GUI → CLI 顺序恢复时保留上下文、Team、模式；同时写入同一会话被阻止 |
| 项目关联 | 无关联不会加载意外 cwd 的上下文或工作工具；绑定项目显示实际起点，未提交内容不会被偷偷纳入或覆盖；CLI 恢复后遵守同一关联 |
| 项目执行 | 通过 GUI 完成含真实修改和检查的任务；ONE 无委派，CoThink 只展示实际参与者 |
| 变化与检查 | diff 绑定起止版本；检查绑定实际候选或最新组合；空策略显示未验证，失败不标完成 |
| 成果交付 | 在临时仓库验证下载补丁可重建对应结果（含二进制／删除／文件模式）；成果目录对应固定版本，原用户目录保持不变 |
| 取消与中断 | 取消覆盖成员与受管进程；已接纳部分成果仍可查；unknown 不自动重做 |
| 连接与重复提交 | 双击、确认响应丢失、刷新和 SSE 重连不额外触发模型；日志分页不会改变任务状态 |
| GUI 实际体验 | 在 1280×800、1024×768、800×600 下中文输入法确认不误发、公式可读、代码可复制、查看历史不强制滚动；右栏关闭恢复焦点与阅读位置，跨页停止入口可达 |

完成 GUI 机制与可用性验收，不等于证明模型质量提升；已有终端测试和历史真实模型批次也不替代 GUI 的上述验收。
