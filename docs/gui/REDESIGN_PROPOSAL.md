# CoThink GUI 重设计方案：围绕项目和成果工作

> **下一轮设计（2026-11-07）：** 用户已确认以项目 Team 组织左栏、精简常驻功能的方向，具体方案见[项目团队设计](TEAM_WORKSPACE_DESIGN.md)。新方案尚未实施；本文保留上一轮设计与证据，不将旧布局或开工授权自动延伸到新一轮。

2026-10-29 设计与可点击原型；2026-10-30 按已确认反馈完成 P0—P5 本地实施，P6 组合与安装验证见 [VALIDATION](../../VALIDATION.md)。本轮仍是未发布候选，运行语义以设计基线为准。具体架构、接口与首轮范围见 [重设计施工方案](REDESIGN_IMPLEMENTATION_PLAN.md)。

## 1. 要解决的问题

用户明确主要用于**编程和文件制作**。目标是让人能顺畅完成：找到项目 → 描述工作 → 提供材料 → 知道当前进展 → 看文件或改动 → 提出修改 → 取走成果 → 归档对话，之后还能找回。

“如无必要，勿增实体”在这里意味着：每个对象、入口和默认显示的信息，都必须帮助上述某一步。减少操作负担不能只靠把内容藏起来；归档、恢复、搜索、文件引用、成果预览这些必要操作需要补齐。

本文描述目标体验；首轮正式施工范围见[施工方案](REDESIGN_IMPLEMENTATION_PLAN.md)第 1 节。文件引用、真实附件、历史分支和执行网页脚本属于后续增量，不能把目标体验直接当作第一批已支持的功能。

本轮范围是整体信息结构和交互重设计，不是换一套配色。保留唯一 CLI／GUI 核心、Pi 会话、Team 快照、任务记录和 agent-sync 边界。下面保留最初设计的理由和目标；具体已实现范围、机制验证与未验项以施工方案和 VALIDATION 为准。真实模型质量和用户使用偏好未由 fixture 或代码检查证明。

## 2. 重设计前的界面审查（2026-10-29）

当时的审查对象为 `0.8.7-modes.1` 源码及本地隔离演示，以下表格保留改造前事实。实际查看了窄窗口、1366×900 桌面空状态、项目接入、项目对话、部分完成、变更面板、模型组合和项目执行设置。演示只使用 localhost 固定回复和临时项目。

一次既有 `GUI_WORK` 演示在当前运行协议下返回“领导草稿尚未接纳”，没有完整成果。本次保留它用于审视失败界面；**不据此判定真实项目执行存在同一故障，也不把这次演示计作成功任务验收**。成功成果的呈现另以组件源码核对。DSH 核对的是本地源码，Codex 核对的是当前官方文档。

| 当前可核对的事实 | 对工作造成的负担 | 重设计决策 |
| --- | --- | --- |
| 桌面空状态就显示约 240px 的“本轮协作”，其中只有宣传文案 | 尚无任务时占用工作区域；进入工具却先读介绍 | 空任务不出现右栏，删除重复宣传语和大幅欢迎标题 |
| 左栏只有标题搜索和对话按钮；没有归档、恢复、置顶菜单 | 已完成工作持续堆积，无法保持工作列表可用 | 补齐对话整理；默认只列未归档对话 |
| “最近对话”计数取全部筛选项，实际这一段只显示无项目对话 | 分组名称、数字与可见内容不对应 | 列表数量只对应当前范围；没有作用的数量不显示 |
| 项目组默认全部展开；没有项目内的新对话入口 | 项目多时列表很长，创建操作与当前项目脱节 | 项目折叠状态保存；项目行就近新建对话 |
| 新建对话默认无项目；“打开项目”实际上创建另一个关联对话 | 开始工作时容易选错上下文 | 全局新建继承当前项目，明确提供“无项目”；打开项目与新建对话各有清晰含义 |
| 项目接入先输入绝对路径，再读 HEAD、正式起点和 JSON | 用户必须先理解内部执行机制 | 提供宿主目录选择和最近项目；只前置会影响任务的检查结果 |
| 输入区同时有模式、Team、思考、配置、两套政策说明及“制作HTML/SVG／发送” | 提交前要理解多个层级，两种提交入口容易混淆 | 一个发送按钮；模式常驻，模型组合与参数按需展开 |
| 变更面板上方仍保留成员、冻结阵容、未参与成员、用量等 | 想看改了什么，先经过大量协作信息 | 文件／变更区域只呈现与交付有关的信息 |
| 文件列表只是文本标签，diff 是整段拼接文本；起止版本和集成 ref 先于内容 | 难以逐文件审阅，内容被技术事实压到下方 | 可选文件列表、逐文件差异；版本信息放“版本详情” |
| 已有截图证据和打开成果目录，但没有统一的成果文件阅读路径 | 制作文件后仍要找它在哪里、怎么打开 | 回复直接给出可点击的成果文件，接入同一阅读区域 |
| 默认界面没有文件引用／附件入口；也没有从消息处分支的 GUI 操作 | 给修改依据、提供参考图、尝试另一种方案不顺畅 | 分阶段补文件引用、有限类型附件、从这里新建对话 |
| 失败展示“领导草稿尚未接纳”等内部术语；多条横幅可能同时出现 | 无法快速判断保留了什么、接下来能做什么 | 统一以“结果状态、保留内容、下一步”表达异常 |
| 更新摘要首次启动以模态框出现；设置把更新拆成两个分类 | 更新信息抢占开始工作的流程 | 偏好与更新合并，普通更新使用可关闭提示 |

对应源码：`gui/src/App.jsx`（导航、横幅、回复、空状态），`Composer.js`（输入），`Collaboration.jsx`（成员、变更、检查、截图），`ProjectDialog.jsx`（项目接入），`Settings.jsx`（设置），`src/gui-controller.js`（现有操作范围和单活跃任务约束）。

值得保留：正文 Markdown／公式／代码能力；本地运行；草稿保存；当前模式可见及 Option+M；历史真实来源；取消与部分结果保存；项目改动不自动写回；已有焦点管理和键盘可达性。

设计审阅的主观评分，以本次工作用途衡量：目标契合 4/10、信息层级 4/10、视觉一致性 6/10、使用流程 3/10、辨识度 6/10。综合约 4/10，优先解决使用流程和信息层级；这些分数不是用户实验结果。最先能产生收益的三项是取消空协作栏、增加归档恢复、让文件先于版本回执出现。

## 3. 参考产品：采用行为，选择性采用结构

| 来源与已核对的事实 | 采用到 CoThink 的做法 | 不照搬的部分 |
| --- | --- | --- |
| Codex／桌面官方文档：项目内组织对话，支持重命名、置顶、搜索、归档与恢复 | 让当前工作容易回来，让结束的工作容易收起；项目与对话保持稳定身份 | 不引入云任务、自动化、远程主机或多种项目类型 |
| Codex 官方代码审阅：在独立审阅区域查看文件与差异，可围绕具体改动反馈 | “看成果”和“继续交谈”能同时进行；反馈可指向文件／行 | 不复制提交、强推、回滚等完整 Git 控制台 |
| DSH `ArchiveSession.tsx`：列表行／菜单归档，归档后可恢复；运行中另有显式处理 | 常用操作靠近对象；归档可逆，活动任务另作明确处理 | CoThink 不照搬复杂活动类型和归档确认编排 |
| DSH `WorkspaceBrowser.tsx`：项目分组、搜索、置顶、归档筛选；`AppFrame.tsx`：右栏按内容需要占位，可收缩 | 导航围绕持续的工作；右侧按需展示具体文件 | 不引入多套分组、注册表、插件槽位或通用布局系统 |

参考的价值在于操作的位置、层级和连续性。项目工作台也不等于始终摆满三栏。

## 4. 三个方向及推荐

| 方向 | 收益 | 代价 | 判断 |
| --- | --- | --- | --- |
| 精简聊天界面 | 改动最少，问答更轻 | 文件制作和代码审阅仍从属于聊天详情 | 可用于普通问答，不适合作为本次主方向 |
| **项目工作台，成果按需展开** | 项目、对话、文件都有清楚位置；可以边看成果边反馈 | 需要补齐会话整理与文件阅读路径 | **推荐，符合主要用途** |
| 完整 IDE／多面板控制台 | 所有开发工具集中 | 编辑器、终端、Git、面板状态都会显著增加维护和理解成本 | 当前不采用，外部编辑器继续承担完整开发环境 |

推荐方向采用低视觉变化、低动效、适中密度的工具界面。校准值：变化 3/10、动效 1/10、密度 5/10、图片资产依赖 1/10、旧视觉保留 4/10。保留 CoThink 名称与克制绿色；不以大字、人物卡或装饰性动效突出品牌。

## 5. 用户只需要理解的对象

| 对象 | 用户需要它做什么 | 边界 |
| --- | --- | --- |
| 项目 | 知道模型当前处理哪个目录，回到相关工作 | 复用现有目录关联，不再包一层“工作空间” |
| 对话 | 持续推进一件具体工作，保留历史和草稿 | 每次提交仍是内部任务记录，不另建任务看板 |
| 文件／成果 | 阅读、比较、反馈和带走交付 | 从已有任务版本与成果目录派生，不建立独立“作品库” |
| 模型组合 | 指定当前主模型和可用副模型 | 输入区使用 `team` 入口管理现有具名组合，不新增预设／角色系统 |

归档、置顶是对话的展示状态；“成果／变更”是同一批文件的视图；执行记录是已有任务的历史。它们不成为新的业务对象。

## 6. 主工作区

没有打开文件时只显示导航和对话。用户打开成果、引用文件或查看变更后，才出现右侧阅读区域。

```text
┌──────────────────┬──────────────────────────┬────────────────────────────┐
│ CoThink          │ 项目名 › 对话标题    ··· │ 文件名               ↗  × │
│ ＋ 新对话        │                          │ [成果] [变更]              │
│ 搜索             │ 用户：修改页面布局……    │                            │
│                  │                          │ 实际页面／文档／逐文件差异 │
│ 项目        ＋   │ 正在修改文件 · 8次调用  │                            │
│ ▾ 网站        ⋯ │ 执行记录 ▸        停止   │ 文件列表可收起             │
│   首页布局    ⋯ │                          │                            │
│   登录错误    ⋯ │ 完成说明与未完成事项     │ 检查结果紧邻相关改动       │
│ ▸ 课程材料    ⋯ │ index.html  styles.css   │                            │
│                  │ 查看成果 · 查看变更      │ 在文件夹中显示／下载       │
│ 无项目的对话     │                          │                            │
│                  │ ┌──────────────────────┐ │                            │
│                  │ │ 描述要做的事…        │ │                            │
│                  │ │ +  多模型 ▾ team ▾ ↑│ │                            │
│                  │ └──────────────────────┘ │                            │
│ 设置             │ 问答3次／工作不限 · 输出额度说明                       │
└──────────────────┴──────────────────────────┴────────────────────────────┘
```

这是结构示意，文件名、次数和内容只是布局示例，右侧仅在打开内容时出现。

- **左侧找工作。** 项目可折叠且记住状态；置顶对话留在原项目顶部，不在另一组重复显示。运行、失败、未查看结果用小状态标记，不堆满标签。搜索留在导航；查看“已归档”的入口位于左下角设置内。
- **中间推进工作。** 保留问题、真正的结果、用户需要处理的阻碍。当前运行只出现一条进度与一个停止操作。历史回复上的操作归属于那条回复，不能悄悄改看最新任务。
- **右侧看内容。** 打开文件后直接看到内容；“成果／变更”切换阅读方式。不会再在文件上方显示完整阵容、未参与成员、费用回执。关闭后记住用户选择，新事件不强行打开。
- 初次打开某次成果时：有明确、可核验的主要文件则打开它；多个候选时先给文件列表，不猜哪个是最终交付。查看旧成果时保持对应旧版本，不随项目最新进度替换。
- 当前宿主仍只允许一个活跃任务。用户可以浏览别的对话和写草稿；发送受阻时明确指出正在运行哪条工作并提供返回入口。此次设计不承诺后台排队或并行任务调度。

## 7. 对话整理必须形成闭环

**就近操作。** 对话行的“···”提供重命名、置顶／取消置顶、归档。常用归档按钮可在悬停或键盘聚焦时出现，菜单和触屏入口始终可达。先不加入永久删除、垃圾桶、自定义文件夹或标签系统。

**归档。** 空闲对话可直接归档，立即从普通列表移走，并给出“已归档 · 撤销”。不删除对话、模型快照、原文、版本、文件或成果目录，也不触发模型调用。归档当前对话后回到该项目的最近未归档对话；没有则显示新对话入口，避免悄悄创建一条新记录。

**运行中。** 归档不能隐式取消任务。菜单说明“任务进行中，停止后可归档”，提供返回运行任务；用户显式停止并得到结果状态后再归档。不新增“稍后自动归档”队列。

**恢复。** 从左下角“设置 → 已归档”搜索、查看与恢复。恢复后记录回到原项目，但不强迫跳转当前工作；点击记录才打开对话。保留标题、内容和成果，继续发送前先恢复。普通列表与设置内列表复用同一套行操作和宿主事实。

**搜索。** 支持标题、用户输入和最终回复的本地文本匹配，默认当前项目，可切到全部项目；提供“包含已归档”。结果带项目名、归档状态和命中片段，点击定位对应消息。默认不搜索内部提示词和海量工具日志，不加向量库或语义搜索服务。长列表分段加载；搜索不要求先渲染全部对话正文，损坏记录单独报告，不能让整次检索失效。

**从历史继续。** 消息菜单提供“从这里新建对话”，复用 Pi 分支能力，保留截至选定位置的上下文、模式和组合；原对话不改写。新对话附一个返回来源的链接，不增加可视化分支图。

归档与置顶按会话 ID 保存为宿主的会话级展示元数据，独立于 Pi 分支、模型上下文和浏览器缓存。复用现有原子存储能力；不复制一套会话正文。遇到占用或写入失败，不先把列表隐藏后假装保存成功。持久化位置、writer、并发及空白会话的规则由[施工方案](REDESIGN_IMPLEMENTATION_PLAN.md)统一规定。

## 8. 项目、输入与上下文

### 打开项目

主入口为“选择文件夹”，也允许粘贴路径和选择最近项目。浏览器的目录上传不能冒充宿主路径选择；本地 Node 宿主需要一个受限目录选择／浏览入口，原生选择器可作为平台增强，不因此更换应用框架。

选择后自动执行只读检查，默认只显示：项目名称、是否可开始、需要用户处理的问题。HEAD、集成引用、镜像 digest 和原始检查配置放入“环境详情”。“已配置”与“实际运行检查通过”必须区分。

有未提交修改时，在开始工作前明确说明它们是否包含在真实工作起点；不能藏进详情，更不能假装已经纳入版本。当前 core 仍要求 Git 项目，非 Git 文件夹必须说明限制。若提供“初始化后作为项目使用”，需要明确由用户点击，并作为独立的 CoThink 适配工作，不自动修改目录，不绕过 agent-sync。

已开始的对话不直接更换项目，因为其历史与权限已绑定。用户选择另一目录时新建关联对话，可带走尚未发送的草稿；原会话保留。

### 一个输入框，一个发送按钮

- 默认只留“添加材料”、**多模型／单模型**、`team` 和发送。多模型对应 CoThink，单模型对应 ONE，沿用 Option+M；不新增模式。
- `team` 按钮和 `/team` 打开同一面板，支持选择、新建、调整后另存和删除；主副模型、顺序、思考和输出额度在该处管理。当前使用的组合和最后一个组合不能删除，允许两个删到一个；旧对话保留快照，新对话继承最近合法选择。输入区不一直展示所有服务商和参数字段。
- “制作 HTML/SVG”从第二个发送按钮改为“+”菜单中的本次操作。选中后在输入区显示一个可移除的“制作网页”标记，仍按同一个发送按钮；提交时映射现有 `workRequest`，一次提交后清除，不变成持久模式。
- 项目文件引用通过 `@` 或“+ → 引用项目文件”添加。显示路径及读取来源，不静默引用整个目录；涉及旧版本或未提交内容时说明读取的是哪份内容。
- 输入区下方保留一条真实政策：例如“问答 3 次／工作不限 · 未设本地输出上限”。有额度时显示已设额度的摘要和展开入口。长篇默认超时、压缩、预热及计费说明移入详情；未知费用不显示为 0。
- 运行中输入是草稿，不能伪装成会自动发送的排队消息。切换模式只影响下一条，当前任务保留提交时冻结值。Enter／Shift+Enter、中文输入法、焦点和草稿行为保持。

材料支持按实际能力交付：先完成项目文本／代码引用；图片输入须核对实际模型和请求适配。PDF、DOCX 等不能只显示“上传成功”却没有解析能力；未支持时在发送前明确告知，不为本轮增加通用资料库。

## 9. 成果、改动和下一步

**回复先给交付。** 结果说明之后直接列出真实存在的文件及“查看成果／查看变更”。文件列表、检查状态和操作属于这次交付。没有成果目录时直接说明“还没有可交付文件”，不让灰色按钮成为唯一解释。

**文件阅读。** 文本和代码只读查看；Markdown 渲染；图片使用已有截图能力。HTML/SVG 先保证现有固定版本截图与实际文件可达；交互式 HTML 预览作为单独扩展，须隔离运行、限制网络，并与 GUI 启动凭据隔离。不把任意生成脚本直接放进应用同源页面执行。

**其他文件。** 已生成的 PDF、DOCX、PPTX 等至少支持下载或在系统应用／文件夹中打开；内嵌阅读逐种适配，不声称当前已经支持制作或解析所有格式。文件选择器只列当前任务成果和明确授权的项目范围。

**逐文件看差异。** 文件名可点击，默认显示所选文件的差异，保留增删与检查状态。二进制文件显示类型和是否改变，不伪造文本 diff；无变化时明确显示。起点、终点和实际贡献范围在“版本详情”中可查，不能把整个版本区间的改动都算作某一个成员的贡献。

**反馈回到对话。** “引用文件／选中片段询问”只把位置与必要片段放入草稿，由用户发送。暂不增加独立评论数据库或多人评审流程。

**把成果带走。** 保留“在文件夹中显示”和“下载补丁”，补齐按文件下载。交付摘要明确“已保存到独立成果目录，原目录未修改”。本轮不增加自动写回、强推或绕过检查的“接受全部”按钮；未来如果需要一键应用，必须单独设计冲突与回退语义。

**看过程。** 每条回复只保留“执行记录”入口，展开已有成员、工具、评审与处理理由；原文不删，角色与来源不改写。默认不展示未调用的全部成员。视觉模型的“符合／不符合／不确定”仍是模型判断，和文件已保存、截图完成、检查通过各自表达。

## 10. 状态与异常的统一表达

| 情况 | 默认显示 | 详细信息与动作 |
| --- | --- | --- |
| 执行中 | 正在修改／检查文件，已用时间；停止 | 展开执行记录；不制造完成百分比 |
| 完整交付 | 结果说明、文件、检查结论 | 查看成果、查看变更、下载／打开 |
| 未配置检查 | 已保存，未运行检查 | 解释检查策略；不显示“测试通过” |
| 部分完成／取消 | 未完成的部分、已保留的内容 | 查看已保存文件和记录；停止不等于回滚 |
| 提交结果未知 | 尚不能确认是否已提交 | 读取原提交状态，草稿保留；不自动再发，不提供无差别重试 |
| 会话占用 | 此对话正由其他入口使用，当前可阅读 | 定位相关入口；不设计破坏锁的“强制接管” |
| 设置或材料阻塞 | 具体缺什么、影响哪次任务 | 就近修正，保留输入；不只给技术错误串 |

“领导草稿尚未接纳”这类原始诊断可放详情。面向用户的摘要应说清“本次修改尚未成为已保存成果”，并依据实际记录说明是否有可查看的草稿；没有证据时不能承诺已经保存文件。

避免同时出现更新、运行、连接、错误四条横幅：运行状态贴近当前任务；更新去设置角标；正常连接不常驻占位；断连、未知提交等阻断操作的信息才使用醒目提示。严重状态不能被普通 toast 覆盖。

## 11. 设置与视觉规范

正式设置保留四个分类：**已归档、模型与认证、项目执行、偏好与更新**。Team 编辑由输入区的同一 Team 面板负责，设置不复制另一套阵容表单；服务商认证仍复用原有数据边界。原型说明、重置示例不进入正式设置。新增模型时就近填写认证；保存不等于远端验证，不自动发起收费测试。初次组合可建议名称，由用户保存确认；阵容改变仍另存，旧历史不回写。

项目执行先显示已配置的执行环境与检查策略，再展开镜像、资源限制、命令参数等高级内容。保留全局设置对后续任务生效的真实作用范围，不仅因为页面位于某个项目内就假装它是项目专属配置。

视觉采用工具而非宣传页的密度：系统中文无衬线字体；正文 15–16px，导航／控件 14px，辅助文字约 12–13px；8px 间距节奏，4px 用于紧凑控件；边框和小圆角用于区分可操作区域，减少嵌套卡片。主色继续使用克制绿色，只强调选中项和主要操作；错误及检查状态另用语义色。正文和主要控件以至少 4.5:1 对比度为目标，不能通过变成浅灰来隐藏复杂度。

移除 `A LITTLE MORE PERSPECTIVE`、`THIS TURN`、`YOU /01` 等装饰性层级，减少对话两侧重复标语。空状态给一句“在这个项目中要完成什么？”和输入区，必要时提供打开项目／配置模型的实际操作。

布局以实际可用宽度决定：左栏约 220–240px；对话正文合理限宽；文件阅读优先留出约 560px 以上。总宽不足时先收导航，仍不足则让文件阅读临时占满工作区，提供清楚的返回入口并恢复草稿、滚动和选中文件。禁止为了固定三栏把代码挤进细条；关闭面板后不被新事件抢回。动效仅用于展开、关闭和状态反馈，支持减少动态效果。

## 12. 实施范围与顺序建议

| 阶段 | 要交付的用户能力 | 主要边界 |
| --- | --- | --- |
| A：整理工作与减负 | 归档／恢复／置顶／重命名、项目内新对话、搜索、默认两栏、一个发送入口、状态文案整理 | 展示元数据要持久保存，CLI／GUI 共享身份；不改调度和模型调用路径 |
| B：成果可用 | 按文件查看差异、真实文件预览／打开／下载、检查紧邻成果、历史版本对应正确 | 用已有任务和版本数据；先完成当前支持格式，任意网页交互预览另做隔离 |
| C：提供材料与继续工作 | 项目文件引用、受支持附件、从历史分支、宿主目录选择和更顺的首次配置 | 需要真实接口能力，不能只画上传按钮；不扩展 agent-sync 权限 |

A 与 B 是这次重设计的第一批完整交付，不能只完成“界面变简洁”就宣布结束。C 按实际材料类型继续补齐。更换 Electron／Tauri、完整 IDE、终端常驻、多任务并行、插件市场、自动化、标签／文件夹系统、投票与共识分数均不在本轮范围。

上表保留设计阶段的顺序建议；2026-10-30 获批的实际施工与验收范围已细化为 [P0—P6](REDESIGN_IMPLEMENTATION_PLAN.md)。C 中的文件引用、附件、历史分支和宿主目录选择仍属后续增量。

## 13. 用真实操作判断是否更好

以下保留设计时的用户路径目标。首轮已取得的本地机制／浏览器证据见 VALIDATION；第 6 项的文件引用仍属后续范围，物理中文输入法与真实用户偏好未验证：

1. 从已有项目新建对话并发送，不要求重新输入路径、重命名模型组合或理解内部 ref；开始前看得出实际项目、模式和额度政策。
2. 对话行能直接找到归档；归档后从普通列表消失，重启仍有效；在已归档视图搜索到它，恢复后原内容、成果和项目关联仍在。全过程零模型调用。
3. 运行中的对话不会被静默取消或隐藏；切到别处的草稿不丢、不自动排队，能返回活动任务。
4. 制作 HTML 或修改代码后，从回复可直接打开成果或逐文件差异，默认阅读区不先展示阵容和长哈希。旧结果打开的仍是旧版本。
5. 没有文件、未运行检查、部分完成、未知提交四种情况明显不同；不把“成员结束”画成“任务成功”，不把保存画成写回原目录。
6. 用户能把一个项目文件作为明确上下文引用；不支持的附件在发送前解释；切换面板后草稿与引用保留。
7. 只用键盘也能选对话、打开菜单、归档恢复、读文件、返回输入。中文输入法、Option+M、Shift+Enter 和 Esc 不冲突。
8. 在正常笔记本宽度和窄窗口中，用户能看清当前对象和主要操作；没有空右栏挤压正文，也没有三层嵌套滚动容器妨碍读代码。

验证优先使用这些真实用户路径及已有回归。只有现有验证没有覆盖归档持久化、旧版本文件对应等关键约束时，才补充对应测试；不以 DOM 数量、组件内部状态或新增测试数量代替可用性。

## 15. 方案自审

推荐的用户对象均有当前使用需求，视图没有另造模型／调度实体。必要功能与技术债已区分：归档、文件接口、附件与目录选择确实需要宿主支持，不能用前端样式承诺完成；完整 IDE 和多任务并行暂不增加。单活跃任务、共享核心、历史快照、未知不重发、正式版本及不自动写回保持一致。方案的主要待验证判断是：按需展开成果是否比常驻成果区更顺手，应在可点击原型中用真实工作路径比较，而不是再通过代码检查给设计打“通过”。
