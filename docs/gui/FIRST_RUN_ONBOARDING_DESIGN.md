# CoThink 桌面端：从首次打开到第一条回复

2026-11-18 · 已在本地桌面维护工作树实现。安装与验收状态见 [VALIDATION.md](../../VALIDATION.md)。

## 用户会经历什么

第一次打开 CoThink，用户应该能独立完成两步：**为自己的项目创建 Team，给第一条对话选好模型。** API Key 在选模型时填写。点「开始对话」后，光标就在这个项目的输入框里；用户自己发送问题，第一次真实回复才说明主模型能工作。

例如，一位新用户想用 CoThink 准备组会，手里只有一家服务商的 Key。如果这个账户能用两个适配型号，他可以选「组会准备」文件夹作 Team，用同一把 Key 配好一主一副，直接问自己的问题。未选第二个不同型号时，提示“副模型可以来自同一家服务商”；也允许选另一家。目录能识别型号和重复席位，不能判断账户实际开通了哪些型号。

| 时机 | 用户看到、需要决定的事 | CoThink 负责的事 |
| --- | --- | --- |
| 首次打开 | 首页主按钮「创建我的第一个 Team」。旁边一句：“一个 Team 对应一个项目，可以在里面开多条对话。” | 沿用现有首页，仍可先写草稿。只有正常读取到没有 Team 的首页才显示首次文案。 |
| ① 创建 Team | 「为这个项目选一个文件夹」。文件夹名自动成为建议名称，可直接用，也可改。说明每条对话的成果会放进自己的子文件夹。 | 复用新建 Team 窗口。首次入口只决定项目，以 `defaultRosterId: null` 创建；即使已有阵容也放到下一步选。日常新建 Team 保留原来的默认阵容选项。 |
| ② 配置阵容 | 主模型：“你直接与它对话，由它负责交付。” 副模型：“需要协作时，主模型可以请它参与。” 初始只展开一主一副，保留增加副模型的入口。已有阵容可直接选；没有阵容时给第一套预填可改的名字“日常协作”。 | 在原阵容编辑器中完成。同一家服务商只出现一个认证区；已有认证直接复用。缺 Key 时用密码框填写，点「保存 Key」后留在原处，标明“已保存，尚未验证远端权限”和“费用取决于服务商与账户”。 |
| 开始对话 | 主按钮「开始对话」，旁边说明“这个 Team 的新对话也将默认使用此阵容，以后可以更换”。 | 将选定阵容用于第一条对话，并设为这个 Team 的默认值。回到原输入框，保留已有草稿，不发送示例、不发测试请求。 |

选模型时优先展示支持统一会话的型号。不支持的型号不可选；只差 Key 或协议必填输出额度的型号可以选，并在对应位置告诉用户还缺什么。必填额度直接展示，单位是 tokens；其余参数保持收起，沿用现有思考档位。点「开始对话」前须先保存缺少的 Key，不把输入框里尚未保存的内容当成已配置。Key 旁给一句取得方法；有已核实的服务商官方入口才提供链接。

自定义地址、OAuth 和环境认证沿用「设置 → 模型与认证」。存在未保存编辑时，先让用户选择继续编辑或放弃。关闭设置后回到原对话的阵容配置，可用已保存的凭据重新选择模型。

## 怎样接到现有代码

界面上的 **Team** 在源码里叫 `workspace`；**阵容** 在接口里叫 `team`；对话是 `session`。这三个对象已有独立的保存与恢复规则。第一版只改变入口、文案和几个现有动作的顺序。

1. **从首页进入。** 在 [Conversation.jsx](../../gui/src/features/conversation/Conversation.jsx) 的首页空态增加主按钮，复用 [App.jsx](../../gui/src/App.jsx) 的 `create-team` 弹层。在同一空首页点主按钮、左栏新建、或先写草稿再发送，都走同一入口；有项目时沿用日常操作。[ProjectDialog.jsx](../../gui/src/ProjectDialog.jsx) 已有桌面选目录、浏览器目录选择、建议名称、重复目录和原操作查询。选到已被占用的目录时沿用「打开已有 Team」，不重复创建或替它写默认。
2. **等第一条对话真正打开。** [useGuiWorkspace.js](../../gui/src/useGuiWorkspace.js) 的 `createWorkspace` 已在保存项目后调用 `createSession`，首页有编辑稿则走 `transferHome`。不要在引导完成时再建一次。`ProjectDialog.onSaved` 收到的是项目回执，不能当作对话就绪。引导只在已打开的可写对话确属刚建 Team 时继续；用户已切换到别处就不抢焦点。有可用默认阵容且 `session.team` 已绑定，直接落到输入框；否则转到原阵容弹层。
3. **在原编辑器中完成配置。** [TeamPanel.jsx](../../gui/src/features/teams/TeamPanel.jsx) 已有阵容列表、新建、按服务商保存 Key 和保存结果核对；[ModelEditor.jsx](../../gui/src/features/teams/ModelEditor.jsx) 已有目录、席位去重和额度字段。无已存阵容就从新建表单起步，有阵容就从选择起步。现有就地认证仅在编辑草稿时出现：将同一块服务商认证区同时用于「选中的已有阵容」，沿用 `saveProvider`。旧阵容只缺 Key 时补认证、刷新后用原 ID，不另存副本。需更换现有 Key 或高级认证时进入 [ProviderSettings.jsx](../../gui/src/ProviderSettings.jsx)。
4. **显式完成两种绑定。** 「开始对话」先检查所选各席位的本地配置；新阵容才执行 `team.save`。随后沿用 `selectTeam({sessionId,teamId})` 绑定目标对话；确认后用 `commands.updateWorkspace(workspace,{defaultRosterId:team.id})` 保存项目默认，命令会带上项目 ID 和版本。两处均已是目标值时不重复写。若项目版本冲突，读取当前默认：已是目标即完成；别人已选不同默认则保留，当前对话仍可聊。日常阵容管理仍可仅保存、仅切换当前对话或单独设默认。后续新对话继承默认，其他已有对话保留自己的快照。

席位及可用性以 [config.js](../../src/config.js)、[saveGuiTeam](../../src/gui-settings.js)、[projectModelFacts](../../src/pi-model-runtime.js) 和 [GUI 宿主](../../src/gui-controller.js) 为准。模型引用按 `provider/modelId` 去重；同一模型可担任多个工作岗位，这是任务调度，与阵容席位不同。前端不能拿 `bootstrap.configured` 当“首次引导完成”（它只表示有 v3 配置），也不能用 `models[].available` 一个布尔值筛掉所有缺认证或缺必填额度的型号。首条普通消息继续由原输入框、原提交入口和现有预算处理。

## 中断、已有用户与重开

判断依据是当前项目、对话和阵容的已存事实。只在用户主动进入这次流程时连续打开两步；重开后在缺少操作的地方给按钮，不反复弹窗。无需保存 `onboardingCompleted` 或“当前第几步”。

| 看到的实际状态 | 界面下一步 |
| --- | --- |
| 正在加载／重连、项目表不可读、归属或历史待核对；或用户只有归档 Team／正在看旧历史 | 保留原来的加载、恢复或历史界面。空数组与不可读分开；不把旧用户带入首次流程。 |
| Team 已保存，第一条对话创建失败或结果未知 | 保留 Team。已知未成功时可继续创建。未知时用原 ID 查询，不自动再建。普通创建的待查 ID 在 `sessionStorage`；带首页草稿的创建另有宿主保存的预留 ID。完整退出且没有原 ID 时，先核对此 Team 的已存对话，能确认就打开；不能确认就交给用户判断。 |
| 目标对话尚未选阵容，或退出时只保存了认证／阵容 | 从原输入框的「选择阵容」继续，复用已存认证和阵容。普通选择仍仅绑定当前对话；想让后续对话沿用，可点原有「设为此 Team 默认」。不因进入旧对话替用户补写默认。未保存的 Key 不写入草稿、浏览器存储或日志。 |
| 已绑定当前对话，Team 默认未保存 | 提示“当前对话已可用，新对话的默认阵容未保存”，可直接「返回对话」或单独重试设置默认；写入结果未知先读回核对。重开后无法区分“上次失败”和“用户主动不设默认”，只保留普通的「设为此 Team 默认」操作。 |
| 已有可写对话且已绑定阵容，首问的单次模型请求确认失败 | 保留原问题和服务错误。如果已有请求记录能确认实际型号，就在回复下显示服务商和型号，并提供「检查模型与认证」「更换阵容」。修正后由用户发送下一条消息。 |

## 为什么只做这些

只在首页放三个指向设置的链接，代码最少，但用户还得自己找回第一条对话，并分清“保存阵容”“用于当前对话”和“设为 Team 默认”。独立做一套向导可以控制所有页面，却会复制认证、目录选择和保存恢复逻辑。**推荐用首页入口串起原来的两个表单。** 以后增加模型、认证方法或副模型席位时，只更新负责这项能力的现有界面。第一版无需新增服务端接口、配置格式、引导进度表或模型调用；不强制连接测试，用户的第一条真实问题就能检验主模型。

## 交付时怎么判断做对了

- **先验主路径。** 用隔离数据目录、一个有两个适配型号的本机模拟服务商，从 GUI 首页选文件夹，只填一次 Key，点击「开始对话」。此时恰有一个新 Team、一条项目对话、一个新阵容；当前阵容和项目默认都指向它，模拟服务收到零次生成。用户发送一条简单问题后，在同一对话看到预设回复；再开一条对话能继承默认。
- **覆盖真正会打断使用的分支。** 复用现有浏览器脚本：从已有首页草稿开始，丢失第一次创建回执，查询后仍为原对话、材料保留且没有自动发送。已有阵容只缺 Key 时，补一次后以原阵容 ID 进入，不新增阵容。中途重开不重复创建；写默认失败仍能发问；非首次、加载失败或已切换项目时不打断当前工作。认证、席位去重、必填参数由原组件用例覆盖。
- **用新用户验证“引导”。** 请未用过 CoThink、持有适配服务商 Key 的人，用干净安装完成一次自己的提问，全程不给口头提示。记录卡在哪一步、是否需跳出设置、是否知道成果放在哪里。另请一位从未创建过 Key 的人尝试通过帮助入口获取；若多人停在这里，优先修服务商指引，而非增加团队配置页面。

**本次已验证。** 在上述维护工作树核对代码，并重跑 8 个已有回归用例，涉及[项目创建与草稿恢复](../../test/gui-team-creation-visual.test.js)、[导航与中断](../../test/gui-components-team-navigation.test.js)、[阵容及认证](../../test/gui-components.test.js)、[从空配置到普通回复](../../test/gui-integration.test.js)，全部通过。另用临时数据目录和本机 HTTP 模拟服务，按方案实际调用现有接口验证两条路径：

- 无项目、无阵容、无该服务商认证：保存一次 Key，两席位绑定到原对话；配置期间零生成，提交首问后主模型回复一次，新对话继承默认。
- 有阵容、无该服务商认证：先建 Team，再补一把 Key。当前对话和 Team 默认均指向原阵容 ID，阵容数仍为 1；配置期间零生成。

以上探针用于施工前核对现有接口。实现后的浏览器验收及尚待真人试用的范围见 [VALIDATION.md](../../VALIDATION.md)。
