## 1. 目标与取舍标准

用户打开 CoThink，应能找到正在做的项目，交代任务，看结果，并在下次回来时继续。日常路径只有：

**选择 Team → 继续或新建对话 → 提交任务 → 阅读交付 → 继续工作。**

每个入口都必须回答一个具体问题：我在哪个项目？现在能做什么？是否需要我处理？成果在哪里？按以下规则决定去留：

- **常驻：** 完成主要路径必须用到，或隐藏后容易在错误项目、模式下操作。
- **按需出现：** 只在某个对象、状态或任务中有用；入口跟着该对象出现，不要求用户记住隐藏手势。
- **删除：** 不能解决当前具体问题，已有入口能够承担，或底层没有相应能力。
- 失败、未知结果、实际阻塞和停止入口不靠折叠换取整洁。隐藏展示不等于删除记录、取消校验或扩大权限。

本次从三个方向中选择“项目团队”：继续以对话列表为中心会让长期工作被历史淹没；照搬独立 Bot 名册会增加找人和转述负担；每个项目一个 Team 能让用户围绕要完成的事情回来。无归属历史继续保存并经全局搜索可达，不为每条旧聊天创建 Team。

## 2. 用户需要理解的关系

| 名称 | 在界面中表示什么 | 必须保持的边界 |
| --- | --- | --- |
| Team（项目团队） | 一个项目的长期入口，包含相关对话及其成果 | 改名、换模型都不产生另一个项目；不强迫学习或讨论项目绑定目录 |
| 对话 | 项目中一件具体事情的连续交流 | 同一 Team 可以有多条；草稿、分支和上下文各自保留 |
| 模型阵容 | 当前对话实际采用的具名主副模型组合 | 复用现有 Team 配置与快照；不新建人物、人设或角色管理系统 |
| 成果 | 某次任务实际产生的文件、答案或改动 | 仍属于原任务，通过对话找回；不另建作品库 |

新 GUI 用 Team 表示项目团队，现有模型组合入口改称“阵容”。底层 `team` 字段与 CLI `/team` 的原含义保持不变，避免为展示改名重写历史格式。文档和诊断同时涉及两者时，明确写“项目团队”或“模型阵容”。

### 2.1 目录与上下文

新建 Team 只要求名称，目录可选。先选目标 Team 的有效默认阵容，再考虑来源对话仍有效的阵容或全局最近阵容；没有可用组合，或显式默认已失效时，提示明确选择。没有可用目录时，仍可在中立上下文中问答。

Team 可关联一个可读文件夹。同一默认目录不能重复绑定，不把不同 worktree 按仓库名合并。更换或解除默认目录只影响新对话，已保存对话保留原目录和归属；目录失效时可以继续聊天，依赖该目录的能力需说明原因。

关联不自动提交或初始化。需要实际文件工作时，核对现有 Git 起点，或由用户预览、确认要用于普通目录初始版本的文件。后续改动和接纳不自动写回原目录。

Team 分组只表示归属，不会让模型自动读完该项目所有聊天。当前对话继续自身上下文；新对话按既有规则加载明确关联的项目说明与资源，不自动汇总其他对话，也不增加隐式跨项目记忆。本轮不建设知识库或新记忆系统。

### 2.2 换阵容时什么会变化

- 当前对话顶部的“阵容”只编辑一处，打开后显示本对话实际模型及参数。
- 选择已有组合或另存新组合，默认只改变本对话的后续任务；修改阵容仍须另存新名字，旧组合保留。
- 阵容行菜单的“设为此 Team 新对话默认”独立保存默认值。列表和模型选择器支持搜索；其他已有对话继续各自阵容。
- 新对话按上节规则选择有效阵容；恢复旧对话优先使用其快照。两者不一致时，面板说明差异，不用默认值遮盖实际选择。
- 只要宿主有任务运行，阵容面板就只供查看，切换、保存或删除组合以及修改 Team 默认值均待任务结束；当前任务使用提交时冻结值。历史作者、请求参数和旧成果不回写。

这项区别保留在同一个阵容面板内，避免在“项目设置”和“对话设置”各造一套模型编辑器。身份不明或阵容不可用时，允许阅读历史；开始新请求前就近说明如何选择，不能猜测旧作者。

## 3. 默认界面

默认两栏，右侧没有空面板。下图仅表示信息关系，示例状态不是实际运行记录。

```text
左栏                         主区
新对话   新建 Team   搜索    CoThink 开发 / 当前标题    对话⌄  阵容
                             用户提出的任务
CoThink 开发  · 有新结果
LLM 学习                     完整交付
课程作业  · 需处理            成果文件          查看过程

                             描述下一步……
设置                         ＋   本次选项              发送
```

### 3.1 左栏：找到持续的工作

[Team 头像候选](TEAM_AVATAR_IMPLEMENTATION_PLAN.md)在左栏显示圆角方头像和必要的真实状态。指针移入头像即播放，停留 2 秒显示名称及必要的同名目录提示，移出即复位。搜索始终可按名称和目录区分 Team。未安装该候选的早期版本仍直接显示 Team 名。本轮不增加行内摘要或模型请求。左栏不显示最近对话分区或可展开对话树；侧栏顶部和主区“对话”均可新建，可明确选择未分组范围。

列表按用户最近打开的顺序排列；后台输出不让列表持续跳动。选中项明确突出。有目录的同名 Team 就近显示短目录提示，完整路径放详情；两个无目录 Team 不允许重名，包括已归档项，提示改名或打开已有项，不增加编号或新的分类系统。

搜索默认查找 Team 名称和已有对话内容，结果注明归属并定位到匹配的对话／消息；涉及已有成果引用时打开其所属任务的文件。项目内的“对话”入口提供当前 Team 的历史及搜索，两者复用同一检索能力。归档结果通过搜索中的“包含归档”显示，平时隐藏该筛选。

无项目的历史与随手提问仍保存，并非无痕或自动删除。通过全局搜索仍可打开“未分组对话”；空白首页可直接输入，首次发送才创建未分组会话。归属待核对的记录不显示成合法未分组历史。

### 3.2 主区顶部：定位与少量入口

顶部保留当前 Team 名称、“对话”切换入口与“阵容”。当前对话标题与 Team 同一行显示；列表用真实活动时间、摘要和状态区分同名历史。

- 点击 Team 名称，查看目录并进入重命名、归档等低频操作。
- “对话”打开最近对话、历史搜索和“新建对话”；不额外建立任务列表。
- “阵容”查看当前组合及实际模型。具体任务的参与者在该任务过程里显示，不摆常驻成员头像墙。

恢复旧对话、打开搜索结果或历史分支时，出现就近的上下文提示，说明正在查看哪条历史；不假装仍处于最近工作。窄窗口收起左栏后，顶部仍提供 Team 切换入口。

### 3.3 对话与输入区

用户消息与最终交付占据主要阅读区域。影响结论的重要分歧、限制和未解决问题留在最终正文，一般评审处理说明收进过程。正文保留 Markdown、中文、公式、代码块与复制能力；长代码和公式在自身区域横向滚动。新结果到来时，只有已在底部阅读的用户随内容滚动，查看旧内容时不抢位置。

输入区保留输入框、发送按钮、“+”菜单和单独的“本次选项”。桌面统一会话已取代旧“单模型／多模型”选择要求；本次导航修正不恢复模式控件，运行合同见[桌面方案](DESKTOP_UNIFIED_IMPLEMENTATION_PLAN.md)。

尊重已有精简反馈：不恢复常驻预算、快捷键说明或一整排参数。“+”用于添加材料、项目文件、可用技能和实际接入的插件入口。“本次选项”显示调用政策，非默认选择以可移除标记留在输入区；模型参数在阵容面板。协议必填额度缺失、配置失效等会阻止提交的问题直接出现在输入处。进入工作后，运行状态明确提示调用次数不设上限，并可查看实际用量。

Enter 发送、Shift+Enter 换行，中文组词确认不能误发。草稿文本与“制作”等本次操作共同属于具体对话；切换 Team、查看成果、打开设置均不能挪走或清空它，插入命令不能直接覆盖旧稿。首次未发送的草稿也要在宿主确认保存后跨重启恢复；未保存成功时保留可复制文本并明确提示，不能显示“已保存”。新对话保存失败时，当前对话、草稿与阅读位置保留；响应未知先查原操作。

### 3.4 右侧：有内容时才打开

点击成果文件、改动或过程时，才打开对应阅读面板；同一时刻集中显示所选内容。文件面板呈现文件／差异，过程面板呈现实际讨论和执行，不互相塞入整套统计信息。

关闭面板恢复原对话的草稿、焦点和阅读位置。空间不足时改为覆盖式阅读，Esc 返回；这不停止任务。宽差异可以扩大阅读区域，不引入多窗格、拖拽布局或持久标签页系统。

### 3.5 视觉演进与当前基准

当前采用[桌面方案 5.1](DESKTOP_UNIFIED_IMPLEMENTATION_PLAN.md#51-视觉精修)的浅色一体窗口、紧凑雾白侧栏与稳定正文底色；本次只修导航关系。用户曾接受的[白色玻璃原型](prototypes/team-workspace-pearl.html)保留为历史参考，不作为恢复旧材质的施工要求。已有明确深色偏好继续保留。

正文保持清晰，不加持续装饰动画、常驻设置条或人物卡墙。正式实现复用现有组件；演示数据、定时回复和原型调节器不进入产品。验收至少包含三个 Team、每个两条对话，不能仅用单项目空白页判断层级是否清楚。

## 4. 每项功能为何存在

下表是本轮可见功能清单。后续要增加入口，先写明用户没有它具体做不成什么，再判断能否由已有入口承担。

| 功能 | 出现时机／位置 | 保留的理由 |
| --- | --- | --- |
| Team 列表与选中状态 | 左栏常驻 | 找回项目，避免在错误项目中继续 |
| 新建 Team | 左栏 | 开始一件需要长期保留的工作 |
| 搜索 | 左栏；项目内搜索在对话列表 | 找回不记得标题的旧内容，补偿左栏收起历史 |
| 未分组历史 | 全局搜索，打开后使用原对话入口 | 保存和找回旧内容，不占左栏一级位置 |
| 对话切换与新建 | 主区“对话”菜单、左栏“新对话” | 同一项目的不同事情不挤进无限长上下文 |
| 阵容与参数 | 顶部一个入口，内容按需展开 | 用户选择实际模型；配置不抢占正文 |
| 输入、发送 | 输入区常驻 | 提交工作；执行方式遵守统一项目会话合同 |
| 材料、项目文件、技能 | 输入区“+”菜单 | 为本次草稿选输入，不扩大访问权限 |
| 调用政策和本次限制 | 输入区“本次选项” | 发送前可核对实际限制和范围 |
| 当前进度与停止 | 有任务运行时 | 知道是否还在执行，并能控制消耗 |
| 返回活跃任务 | 浏览其他对话且有任务运行时 | 单任务执行不因导航变得失控 |
| 需要处理／失败／未知提示 | 对应事实存在时，就近显示 | 防止错误发送、重复请求或误认完整交付 |
| 成果文件与操作 | 对应回复下方 | 直接阅读、反馈、下载或在文件夹中定位结果 |
| 查看过程 | 有相应记录的回复下方 | 检查谁参与、批评与回应，以及失败过程 |
| 差异、检查、版本与用量 | 成果／过程内按需展开 | 评估交付依据；不让版本号和日志先于内容 |
| 复制、从这里分支 | 消息操作，键盘聚焦或悬停可见 | 带走内容或探索另一条路线；复用已有分支，不新增调度 |
| 重命名、归档与恢复 | 对象菜单；恢复在搜索／设置 | 收起完成的工作，仍能找回；不需要永久删除 |
| 设置 | 左下单一入口 | 管理凭据、已有全局资源、环境、外观与更新；低频操作集中 |

“按需出现”必须有可见文字、图标及可访问名称，不依赖只有熟练用户知道的悬停或快捷键。详情不超过一层阅读面板加内容内折叠，不能把故障恢复埋进多级菜单。

本轮从默认界面移除：常驻协作栏、成员卡墙、重复的项目／阵容编辑入口、快捷键教学条、预算说明两行、空成果面板、欢迎宣传卡和无意义计数。已有能力若仍有真实用途，按上表保留次级入口。

本轮不建设：独立 Bot 私聊与 @成员路由、人物设定、任务分派板、项目仪表盘、共识分数／采纳率、独立成果中心、多层目录／标签／自定义分组、多项目并行队列、自动记忆、常驻自治、远程电脑、完整 IDE、自动提交／写回／推送。这些不能由“像 Grok Bot”推导为必要功能。

现有置顶和排序数据保留，不因本轮简化被清空；默认不再为它们设置额外常驻控件。Team 只提供可逆归档，不新增永久删除入口，也不借归档删除阵容、认证、历史或成果。

## 5. 一次完整使用过程

### 开始项目

用户点击“新建 Team”，输入“CoThink 开发”，可选关联目录。已配置模型时直接沿用合法组合；未配置时就近完成一次认证和阵容设置，不自动发送测试题。目录关联只显示会影响开始工作的事实：是否可用、是否存在未提交内容、工作基于哪里；完整路径和版本在详情。

保存后项目入口立即存在，未发消息也不会在重启后消失。Team 的创建不发模型请求、不创建仓库、不自动复制项目。未关联目录时，文件工作入口解释关联要求，普通问答仍可使用。

### 交代与等待

用户说“检查登录流程，先分析，不修改”。任务使用提交时冻结的项目、阵容、材料和选项。普通聊天由主模型回答，按需评审或提出正式项目计划。不要求用户手工把同一任务分发给各模型。

运行中只显示有依据的阶段或当前动作；不虚构百分比，不为“最近进展”多调用模型。用户可查看其他 Team 和写草稿，首版仍是一个 GUI 宿主一次运行一条用户任务。其他对话发送受阻时，说明哪条任务正在运行，并提供返回／停止；任务结束不会自动发送草稿。

### 读结果与继续

任务结束后先显示完整交付；有文件时直接列出可点击成果。文件状态说明保存位置、是否写回原目录及检查结论。“检查通过”“未配置检查”“尚未完整完成”分别表达，部分成果仍能打开。

用户说“先修复第一个问题”，在同一对话继续；换另一件事时，从“对话”中新建。对话名称从首条输入确定，可在菜单里重命名，不额外请求模型。所有成果保留所属对话与任务，搜索找到文件后仍能回到当时的要求和结果。

### 第二天回来

点击 Team 始终恢复上次查看的可用对话、草稿及阅读位置；阅读位置以消息／任务锚点为准，不追求跨窗口逐像素一致。原位置不可恢复时落到最近保存消息并说明，不自动新建或发送。其他对话有新结果或需要处理时，在顶部就近提供“查看新结果／查看待处理”入口，由用户选择前往，不抢走当前阅读位置。历史中的已归档、只读或损坏状态照实保留，提供其他健康对话的入口。

Team 归档后从主列表收起，可通过搜索“包含归档”或设置恢复。含本 GUI 宿主的活跃任务或插件命令时不允许归档；观察到其他入口写占用时提示等待。归档前先确认草稿已保存，不重写内部各对话原有的归档状态。归档约束 GUI 后续提交，不自动取消其他入口已接纳的任务或撤销 CLI 权限。搜索打开归档历史保持只读，开始新工作须明确恢复。

## 6. 简洁界面必须说清的状态

| 事实 | 用户看到什么 | 不能做什么 |
| --- | --- | --- |
| 正在执行 | 当前任务、真实阶段、停止；离开后保留返回入口 | 用装饰动画或旧活动冒充仍在运行 |
| 需要用户回答或处理 | 项目标记“需处理”，选择“查看待处理”后直达具体问题和操作 | 只点开页面就清除尚未处理的问题 |
| 有未读结果 | 项目标记“有新结果”，通过“查看新结果”定位到相关对话 | 打开另一个旧对话就把全 Team 新结果当作已读 |
| 已失败／部分完成 | 说明保留了什么、失败位置和可继续的入口；无待答问题或提交阻塞时按新结果提醒 | 用绿色完成标记覆盖部分结果，或把每个历史失败都变成永久待办 |
| 正在停止 | 停止请求已发出，等待实际确认 | 点击后立刻宣称全部进程已停止或成果已回滚 |
| 连接中断 | 正在重新连接，当前已载入内容仍可读；未载入历史和文件待重连后读取 | 承诺完整离线访问，或把连接故障等同于模型失败并再次发送 |
| 提交或请求结果未知 | 查询原提交／查看已保存状态；草稿保留 | 用一个默认“重试”重复产生外部动作和费用 |
| 保存失败或被占用 | 就近解释，保留内容，阻止依赖失败保存的新提交 | 强抢写锁，或以旧配置继续而不告知 |

左栏只呈现最高优先级的必要状态：需处理优先于有新结果，再是运行中。“需处理”仅由宿主结构化交互或确认仍阻塞后续操作的状态产生；实际答复成功或阻塞解除后消失，不由问句、关键词或所有历史失败推断。普通回答中的提问属于新结果，由正文表达；宿主重启后不保留已失效的交互按钮。单纯失败、部分完成及不再阻塞的未知结果按未读结果提醒，阅读后可清除未读标记，原任务事实不变。前端不能自行判定未知动作已经结束。

行内摘要可说明真实活动；完整事实在任务中，不因只显示一个标记而丢失。空闲时不显示“空闲”徽标。已读位置与任务是否需要处理分开，不另建待办表或“确认已读”流程。

关闭详情不停止任务；关闭浏览器也不等于关闭本地宿主。宿主仍在时可以重连查看，宿主退出后只恢复已保存事实，不自动恢复模型请求。对用户的操作说明放在相关关闭／恢复情境，不长期占据主界面。

## 7. 复用边界与旧数据

### 7.1 已有基础和本次新增要求

以下记录 2026-11-07 开工前的源码核对及相应的设计决策：

| 当前可核对的基础 | 本次应如何使用 |
| --- | --- |
| [导航](../../gui/src/features/navigation/Navigation.jsx)已经按会话目录分组 | 改为项目 Team 入口，历史收进项目内部 |
| [会话记录](../../src/conversation.js)已有项目关联、阵容和分支快照 | 保留原 ID、上下文和历史，不复制一套聊天正文 |
| [GUI 控制器](../../src/gui-controller.js)已有单活跃任务、草稿及提交关联 | 复用提交／查询／取消；补齐未发送草稿跨重启的缺口 |
| [输入区](../../gui/src/Composer.js)已有模式与“+”菜单 | 移位和改名，避免第二套操作路径 |
| [阵容面板](../../gui/src/features/teams/TeamPanel.jsx)已有组合管理 | 原配置继续作为模型阵容；增加项目默认值的明确归属 |
| [文件面板](../../gui/src/features/files/FilePanel.jsx)与[过程面板](../../gui/src/Collaboration.jsx)已有结果投影 | 成果优先，按需阅读，保留真实来源和状态 |
| [目录检查](../../src/gui-work.js)要求有效 Git 项目 | 保留限制；不宣称已支持任意非 Git 目录执行 |

开工前的项目列表主要从会话目录推导，不能独立保存一个“尚无消息的具名 Team”。因此确实需要少量项目展示元数据：稳定归属、名称、可选目录、默认阵容，以及恢复位置和已读位置。否则“先建团队、以后回来”无法成立。复用现有宿主原子保存与导航元数据机制，不新建数据库、模型运行时或权限系统；展示分组不自动成为文件授权。

未发送草稿跨重启、项目未读聚合和完整阅读位置恢复也需要实现与单独验收；不能仅凭已有 `session.create` 或草稿保存按钮认定已经满足。

### 7.2 旧历史进入新导航

1. 按已保存的项目目录关联聚合对话，保留原 ID、分支、原文、任务和成果引用。同一阵容用过多个项目，不据阵容创建或合并 Team。
2. 未分组历史保留原归属，通过全局搜索可达；无目录但已有 Team 的对话仍属于该 Team。缺失或损坏的关联显示待核对，不猜测项目。文件执行仍须通过现有路径与权限检查。本次导航修正不重新执行旧迁移。
3. 同目录的旧对话可能使用不同阵容，全部保留。项目默认值只服务新对话；没有可确认的合法默认时，第一次新建对话再选择，不阻止查看历史。
4. 新增导航数据只保存归属与展示信息，写入失败时旧记录仍可读，不能制造重复项目或把一半迁移当作完成。原有归档、置顶和分支来源不删除。
5. 旧会话恢复仍使用自身快照；历史已删除组合不能被当前默认值冒名替换。CLI 的 `/team` 和原记录格式继续可读可用。

### 7.3 本轮不跨越的运行边界

项目 Team 是 GUI 组织方式。当前 GUI 只有 ONE／CoThink，终端 PROJECT 另有计划、岗位、预算和暂停语义；本轮不增加第三个同名按钮、不伪装已经统一调度。若以后接入，应另行设计真实的计划确认、运行控制和恢复路径。

保留一套 Pi 调用、原有认证与资源选择、父子任务归属和 agent-sync 正式接纳；不回退到旧禁令，也不因为拥有一个 Team 而新增插件权限。普通问答仍一／三次，工作次数政策沿当前入口；已有助手按实际记录展示和计费。无额外命名、分类、状态摘要、自动重试或隐式记忆调用。

正式版本、检查和不自动覆盖原目录的保证继续成立。旧任务缺少来源或版本时如实说明，不以当前状态补写旧事实。

## 8. 如何判断设计可用

下表定义真实入口的验收场景。实际通过的范围及限制见 [VALIDATION.md](../../VALIDATION.md)。

| 场景 | 可检查的结果 |
| --- | --- |
| 已配置用户新建 Team | 只填名称即可开始问答；选择目录后可进入现有文件工作；设置不产生生成调用 |
| 无消息重启 | Team 仍存在，已确认保存的草稿可恢复；保存失败有可读提示和可复制内容 |
| 三个项目来回切换 | 不串草稿、项目或实际阵容；返回上次对话，阅读位置按保存事实恢复；另一对话的新结果通过提示进入 |
| 同项目两条旧对话用不同阵容 | 各自恢复原组合；改变默认只影响新对话，改变当前组合只影响其后续任务 |
| 工作中去读历史 | 原任务继续可见且可停止；其他输入不排队，也不在结束后自动发送 |
| 找一周前的成果 | 从搜索或 Team 内历史直接定位原对话、任务和文件，不必建立成果中心 |
| 完整、部分、失败、未知四种结果 | 用户能区分状态并找到已有内容；重连或双击不重复请求；已读失败不变成永久待办，真正阻塞仍可见 |
| 查看讨论 | 作者、模型、交接和修订来自真实记录；没有虚构插话、共识或未参与者发言 |
| 归档与恢复 | 主列表收起项目，历史／草稿／成果仍在；活跃任务受保护，原对话归档状态不被抹平 |
| 窄窗口和键盘使用 | 800×600 下输入、当前项目、停止可达；中文组词不误发，菜单可聚焦，关闭详情返回原位置 |

至少用“继续昨天的代码任务”“学习讨论中换一个话题”“找回旧文件”走完流程。若用户必须记住某个隐藏位置才能完成这些任务，先移动入口或合并步骤；不以减少按钮数、截图好看或测试数量替代可用性判断。

## 9. 参考依据与待验证判断

Grok Bot 的官方设计以持续 Bot 为中心，过程和工作空间按需展开，并将成果放入对话。CoThink 借鉴其连续工作与渐进展示方式，将一级入口改为项目团队；这是本项目的设计选择，不是 Grok Bot 的原样结构。[官方设计复盘](https://x.ai/news/designing-grok-bot)

官方文档允许按项目给 Bots 分组，并区分需要处理、未读结果和工作状态；这些为导航与状态设计提供参照。[Bot 管理](https://docs.x.ai/grok-bot/bots)、[状态说明](https://docs.x.ai/grok-bot/settings-and-notifications)

群聊通信、持久云电脑和后台工作属于 Grok Bot 的实际产品机制；界面相似不能证明 CoThink 已有这些能力。[协作](https://docs.x.ai/grok-bot/chat-and-collaboration)、[运行机制](https://docs.x.ai/grok-bot/how-grok-bot-works)

初次设计已阅读官方资料、查看官方网页演示并核对相关源码，未登录 Grok Bot 执行任务。随后完成可点击原型，用户接受珍珠白版本；这支持视觉方向，不证明真实保存、模型调用、历史迁移或跨平台行为。项目团队是否更容易理解、隐藏入口能否找回工作，仍需通过正式 GUI 的上述路径验证。
